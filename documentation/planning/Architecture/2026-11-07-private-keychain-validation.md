# macOS Keychain adapter and private-lock validation

This checkpoint records a narrow native acceptance probe for the biometric secret adapter. The existing Anthropic/Codex design reviews and integrated implementation review remain accepted. This probe does not touch recordings, people, actual voiceprints or provider secrets.

## Scope and isolation

The opt-in ignored case `keys::tests::private_native_keychain_item_roundtrip_is_add_only_and_scoped` creates one unique private file Keychain under a newly owned temporary folder. It supplies a random password with `prompt_user(false)` and unlocks only that newly created private handle with the supplied password. Every SecItem operation specifies that private Keychain explicitly. The default Keychain, global search list, global user-interaction flag and security settings are unchanged. The production provider's behavior is unchanged.

The case checks the same generic-password service and canonical-root-derived account convention as production, a missing item before write, a random thirty-two-byte item, exact roundtrip, a second canonical-root instance, duplicate add refusal without replacement, a different-root miss, exact owned-item deletion and absence afterward. Secret bytes and the temporary password are never printed or written to the interruption ledger. Both native probes explicitly create owner-private (0700) folders; the production ledger is 0600. A cleanup guard acquires item ownership only after successful add; normal/panic cleanup deletes only that item. Normal completion closes the temporary folder and removes the private Keychain files. A forcibly interrupted process can leave only its isolated folder/private Keychain; its scoped ledger identifies the temporary account and file for cleanup.

## Why the private path

The pinned `security-framework` 3.7.0 source exposes `ItemAddOptions::set_location(Location::FileKeychain(...))`, `ItemSearchOptions::keychains(...)`, exact service/account selectors, skip-authenticated searches and exact deletion without unsafe code in this project. Its production default-scope password read does not expose a per-query UI-fail policy. Neither the basic private roundtrip nor the production-provider probe changes a process-wide interaction flag. The separately approved physically locked private-file case below uses a scoped process-local guard, supported by the current Apple implementation, while leaving user Keychain policy untouched.

[Apple's current `StorageManager.cpp`](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_keychain/lib/StorageManager.cpp) explicitly keeps private-Keychain creation out of the default search list. [Apple's SecKeychainCreate reference](https://developer.apple.com/documentation/security/seckeychaincreate(_:_:_:_:_:_:)) permits private temporary keychains without user interaction. [Chromium's current scoped-interaction implementation](https://chromium.googlesource.com/chromium/src/crypto/+/refs/heads/main/apple/scoped_keychain_user_interaction_allowed.cc) explains that per-query SecItem UI suppression does not reliably cover file Keychains, so such suppression is not claimed as a guarantee for the production adapter.

## Verification status

The finalized probe compiles; two ordinary cases verify canonical account scope and reject forged/unowned recovery scopes without OS access. Three native/recovery cases remain ignored by default. Strict all-target `vt-speakers` Clippy passes in 1.72 seconds. The explicitly authorized native private-Keychain case passes in 0.85 seconds under a parent-enforced twenty-five-second deadline, using an explicitly owner-private (0700) folder under `/private/tmp`. An earlier preliminary private probe also passed in 1.33 seconds before the harness gained explicit permissions and recovery-scope tests. Real add/read, duplicate refusal with unchanged key, canonical-root agreement, different-root absence, exact owned-item deletion and post-delete absence all pass. No newly remaining private-Keychain folders are present afterward. No actual voiceprint or user/provider credential was used.

## Limits

Private-Keychain SecItem acceptance alone does not prove default-scope production Keychain accessibility; the separate production probe below supplies that evidence for a new temporary item. Access-control continuity across signed app updates, behavior while the user's Keychain is locked and permission dialogs remain unverified. No user Keychain is locked/unlocked and no authentication policy is changed to manufacture those scenarios. No biometric enrollment or matching quality is established by this test.

## Separate production-provider probe scaffolding

A distinct opt-in ignored case, `keys::tests::native_default_probe::production_native_keychain_provider_roundtrip_is_add_only_and_scoped`, exercises the unchanged production `KeychainProvider` against a single random-root-derived account in its ordinary namespace. It never changes the default/search list, interaction policy, lock state or existing keys. It records a durable owner-private temporary ledger before OS access, requires an absent-item preflight, then calls production create/load/create and a canonical-root second-instance load. Duplicate create must return the original key. A different root must find no key. Normal completion deletes only its exact newly owned item, proves it absent and removes the ledger folder. No key bytes or random candidate values are printed.

The root agent inspected and ran this stronger probe in a bounded child after compilation, using an ad-hoc signed copy with the app's identifier, entitlements and hardened-runtime options. It passed in 0.04 seconds without a timeout. A second process using the same signed binary executed its exact helper case and read the newly created key. Duplicate create, canonical-root second instance, unrelated-root absence, exact deletion and post-delete absence passed. Read-only before/after comparison confirmed the user default and search list were identical, and no owned ledgers remained. If OS interaction blocks a future run, the timeout is a failed acceptance result rather than permission to unlock a user Keychain or change user security policy. The exact same compiled/signed test binary contains `keys::tests::native_default_probe::cleanup_interrupted_production_keychain_probe`; it validates the private temporary folder, the canonical child data root, exact service/account derivation and a recorded absent-item preflight before deleting the one test item. A prepared-only ledger authorizes no Keychain deletion. Runtime evidence is retained at `/private/tmp/vantranscribe-keychain-runtime-rcgv0a1v/result.json` and `probe.log`. This proves the production adapter for a newly created test item and the same signed binary across processes; it does not prove access-control continuity between different app signatures or releases.

## Production provider in a signed native probe

The root also executed the unchanged `KeychainProvider` using a copied, ad-hoc signed test binary with the app identifier and existing audio-input entitlement/hardened-runtime setting. The test used one unique owner-private temporary data root and its exact derived account, never a user data root or provider account. Before writing, it proved that account absent and published a mode-0600 interruption ledger under a mode-0700 temporary folder. It then created and read the random 32-byte test key, proved duplicate creation returned the same key, read it through a canonical second provider and a second process running that same signed binary, proved another root could not find it, deleted the exact owned entry and proved it absent. The parent enforces a thirty-second process-group deadline and has exact-ledger recovery, but neither timeout nor recovery was needed. No key bytes are logged.

The probe passed (exit zero) and all owned ledgers were removed. Default Keychain and search-list metadata were identical before and afterward. Evidence is retained in `/private/tmp/vantranscribe-keychain-runtime-rcgv0a1v/result.json` and `probe.log`. This closes native default-scope adapter roundtrip and same-binary cross-process acceptance. It does not establish installed-Tauri-bundle ACL prompts across future signature changes, physically locked-Keychain behavior or Windows credentials. No real voiceprint or private audio was used.

## Physically locked private-Keychain failure

The new opt-in ignored case `keys::tests::private_locked_probe::physical_private_keychain_lock_fails_closed_and_preserves_key` creates a different owner-private temporary file Keychain with a random supplied password. After adding and reading its random test key, it invokes `/usr/bin/security lock-keychain` with only that exact new file path. A data query deliberately does not skip authenticated items, so a locked key cannot be mistaken for a missing key. The test then attempts a duplicate add, unlocks only its private handle with the supplied password, proves the original key is unchanged, deletes the exact owned item, confirms absence and removes the private files. A panic cleanup guard attempts only that same private-file unlock and item deletion.

To prevent unlock UI in this isolated exact-test process, the case reads the existing interaction state and constructs the safe binding's noninteractive RAII guard only when the original state was true; an original false is left untouched. It checks exact restoration on normal completion. Current primary [Apple SecKeychain.cpp](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_keychain/lib/SecKeychain.cpp) implements the setter/getter through `globals().setUserInteractionAllowed`/`getUserInteractionAllowed`; [Globals.h](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_keychain/lib/Globals.h) stores that state in a library `ModuleNexus<Globals>` boolean. This is a process-local library flag, not a persistent user Keychain policy. No installed-app process flag, user Keychain lock state, default or search list is changed.

The exact case passes in 0.91 seconds (0.942 seconds including the parent), under a thirty-second hard deadline covering its process group. The physical locked read returns native `-25293` (`errSecAuthFailed`); duplicate add while locked also returns `-25293`. The original key reads back unchanged after the private unlock. No key bytes are logged. Interaction state is restored, the user default/search list compare equal before and after, no new private folders remain and no timeout occurs. The ordinary key/account and recovery-scope tests pass (two cases; five explicit native/helper cases ignored by default), and strict all-target `vt-speakers` Clippy passes in 1.71 seconds. Evidence is `/private/tmp/vantranscribe-locked-private-keychain-result.json` and `/private/tmp/vantranscribe-locked-private-keychain-probe.log`.

The production adapter maps non-missing native read errors to `KeyUnavailable`; the private fault demonstrates a real authentication failure without manufacturing an error on the user's Keychain. It does not establish the installed app's complete locked-Keychain, permission-dialog or cross-release access-control matrix. Production behavior is unchanged by this test-only increment.
